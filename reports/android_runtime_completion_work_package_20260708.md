## Non-Negotiable Safety Rules

All future Android runtime work must obey these rules.

1. Do not copy the desktop private database to Android.
2. Do not store raw messages on Android until an explicit later implementation slice permits it.
3. Do not store contacts on Android until an explicit later implementation slice permits it.
4. Do not store tokens, credentials, provider secrets, or MCP/agent-channel token values on Android.
5. Do not grant approval authority from push notifications.
6. Do not treat pairing as operator consent.
7. Do not treat app installation as pairing.
8. Do not silently hide unavailable desktop-only features.
9. Do not fake desktop API availability on Android.
10. Do not add broad background sync before pairing, revocation, wipe, retention, and rollback behavior are implemented and tested.
11. Do not make Android source-of-truth for private ForgeLink data in this phase.
12. Keep all degraded/mobile-local states visible to the operator.

## Work Item 010 - Android Pairing Status Surface

### Type

Implementation.

### Purpose

Add visible pairing/trust status to the Android mobile-local runtime surface without granting private-data access.

### Why This Comes First

Pairing is the trust anchor for every later Android cockpit capability. The Android private-data policy and pairing lifecycle report both require pairing status before messages, contacts, notifications, or approval flows expand.

### Scope

Add a pairing status model to the renderer/mobile-local path.

Settings should show one of:

- unpaired;
- pairing requested;
- paired limited;
- revoked;
- lost;
- stale.

Initial implementation may default to unpaired when no pairing data is available.

### Suggested Data Model

A minimal renderer type is enough for the first slice.

Suggested shape:

- state: unpaired | pairing_requested | paired_limited | revoked | lost | stale
- label: human-readable label
- detail: human-readable explanation
- capabilities: string array or simple booleans
- updated_at optional

Do not include secrets.

Do not include device private keys.

Do not include tokens.

### Suggested UI Behavior

In Android mobile-local Settings card:

- show Pairing status row;
- show Pairing status detail text;
- update capability matrix rows for:
  - Push notifications;
  - Device pairing.

Default unpaired labels:

- Push notifications: requires pairing
- Device pairing: unpaired

Paired-limited labels:

- Push notifications: paired limited
- Device pairing: paired limited

Revoked labels:

- Push notifications: unavailable
- Device pairing: revoked

### Suggested Tests

In Electron/renderer/src/App.test.tsx:

- Android mobile-local fallback renders unpaired status by default.
- Android mobile-local fallback renders paired-limited status when shell/mock returns paired_limited.
- Capability matrix reflects unpaired status.
- Capability matrix reflects paired-limited status.
- Private messages remain deferred pending policy.
- Contacts remain deferred pending policy.

### Acceptance Criteria

- Pairing status is visible in Settings during Android mobile-local fallback.
- Default state is unpaired.
- At least unpaired and paired-limited are tested.
- No private messages are stored or displayed.
- No contacts are stored or displayed.
- No approval authority is granted.
- Full tests pass.
- Repo validation passes.

### Explicit Non-Goals

- No QR pairing flow.
- No actual key exchange.
- No private-data sync.
- No push routing implementation.
- No approval from Android notification.

### Recommended Commit Message

Show Android pairing status surface

## Direction Correction - 2026-07-09

The original WI011+ sequence was Android-only and pairing-status-first. That is now superseded.

ForgeLink is targeting cross-platform cockpit parity across Windows, Linux, macOS, and Android.

Android is a first-class ForgeLink communication node, not a permanently limited companion terminal.

Desktop link is a trust and communication-sync relationship. It is not clustering.

See:

- reports/forgelink_cross_device_comms_sync_direction_20260709.md

### Hard Boundary

Do not introduce:

- rqlite;
- Raft;
- quorum;
- voters;
- cluster topology;
- failover;
- HA state;
- clustered control-plane language.

ForgeWire Fabric may inform trust primitives only:

- signed envelopes;
- node identity;
- capability advertisement;
- nonce/replay protection;
- policy gates;
- hash-chain audit;
- operator-visible trust transitions;
- discovery/link setup concepts.

Do not import Fabric's clustering/storage model.
